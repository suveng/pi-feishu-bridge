# 飞书进度展示设计（执行过程可见化）

> 状态：**待评审，未开发**
> 范围：`.pi/ax-feishu-bridge`（桥接自身，不是产品需求）
> 目标读者：维护桥接的人

## 1. 问题

### 1.1 现象

Pi 在本机执行长任务时（一次 `bash` 跑 90 秒、连续几十次 `read`），飞书里那张「回复中」卡片
**正文一个字都不动**。用户无法区分「正在干活」和「已经卡死」，只能干等或反复发消息。

### 1.2 根因

桥接**主动丢弃**了工具执行事件。`src/feishu/reply-card.ts:247`：

```ts
updateFromEvent(_event: unknown) {
  // 不展示过程
}
```

而 Pi 侧一直在发这些事件（见 `docs/json.md:105`）：

| 事件 | 载荷 | 桥接是否消费 |
|------|------|--------------|
| `tool_execution_start` | `toolCallId` `toolName` `args` | ❌ 丢弃 |
| `tool_execution_end` | `toolCallId` `toolName` `isError` | ❌ 丢弃 |
| `text_delta` | `delta` | ✅ 逐字进卡片正文 |
| `message_end` | `message` | ✅ 触发轮末收尾 |

事件其实**已经到了** `updateFromEvent` 里——`PiConversationRuntime.ts:1252` 在 `session.subscribe`
回调中对每个事件都调了一次。所以问题不是「拿不到」，而是「拿到没渲染」。

### 1.3 关键结论

**最小可用改动只需实现 `updateFromEvent` 一个方法**，不需要新的事件通道、不需要改 Pi 侧扩展。

## 2. 目标与非目标

### 2.1 目标

1. 工具执行期间，卡片上能看到**当前在做什么**（工具名 + 关键参数）
2. 单次工具耗时超过阈值时，能看到**已经跑了多久**
3. 「看多少过程」**可配置**，飞书里 `/config` 能改、Pi 侧 `/feishu` 也能改
4. 关闭时可完全退回当前行为（零开销、零视觉差异）

### 2.2 非目标

- ❌ 不做工具**输出**（stdout）回传 —— 那是另一件事，且会泄露大段无关文本
- ❌ 不做思考过程（thinking）展示 —— 隐私与长度都不可控
- ❌ 不改 Pi 侧扩展、不改流式正文的既有行为
- ❌ 不引入 WebSocket / 长连接，仍走 CardKit 的 PUT 全量更新

## 3. 设计

### 3.1 数据流

```
Pi session 事件
   tool_execution_start / tool_execution_end
        ↓  session.subscribe → run.status.updateFromEvent(event)
   ReplyCardStatus（状态机）
        ↓  生成「当前动作」文案，节流后调用
   CardKitStream.setNote(text)
        ↓  复用已有 PUT 通道（pushIntervalMs 节流）
   飞书卡片 note 区刷新
```

卡片结构（三档共用一张卡，只是 note 区内容不同）：

```
┌─────────────────────────────┐
│ 🔄 回复中            [停止]  │
│ ⏳ 正在执行 bash…            │  ← note 区，本设计新增的动态行
│   └ 耗时 42s                 │
├─────────────────────────────┤
│ 我查一下知识库里的…          │  ← body 区，既有逐字打印逻辑不变
└─────────────────────────────┘
```

### 3.2 配置项

新增两个白名单配置（进 `RUNTIME_CONFIG_KEYS`，即天然获得 `/config` + `/feishu config` 入口）：

| key | 取值 | 默认 | 含义 |
|-----|------|------|------|
| `progressMode` | `off` \| `action` \| `steps` \| `timeout` | `action` | 过程展示档位 |
| `progressTimeoutSeconds` | 正整数 | `30` | 超过该秒数才显示耗时（`timeout` 档与 `action` 档共用） |

**各档行为**：

| 档位 | 卡片上看到什么 | 推送频率 |
|------|----------------|----------|
| `off` | 无 note 行，完全等价于现状 | — |
| `action` | 当前工具一行：`⏳ 正在执行 bash…`，超阈值后追加 `└ 耗时 42s` | 工具切换时更新 + 每 5s 刷耗时 |
| `steps` | 每个工具一行，带 ✅/⏳ 与耗时，整轮保留成执行清单 | 工具切换时更新 |
| `timeout` | 平时不显示，单工具超阈值才出现一行 `⚠️ bash 已执行 45s…` | 超阈值后每 5s |

> `action` 定为一档默认：信息量够、不刷屏，功耗与卡长度都可控。`steps` 作为「想全程 trace」的选项。

### 3.3 配置入口（两处，同一份 overrides 文件）

用户要求「飞书或 Pi 都能配」，两条路径都指向 `~/.pi/agent/feishu/runtime-overrides.json`：

**飞书侧（已有命令，零改动）**

```
/config progressMode steps
/config progressTimeoutSeconds 60
/config clear progressMode
```

**Pi 侧（`/feishu` 命令扩展）**

```
/feishu progress steps        # 等价于上面第一条
/feishu progress off
/feishu progress              # 打印当前档位与耗时阈值
```

`/feishu` 子命令走 `src/adapters/pi/index.ts` 的既有 command 分发，需扩一处 switch 分支。

### 3.4 关键实现点

1. **`ReplyCardStatus.updateFromEvent` 落地**
   - 识别 `tool_execution_start` / `tool_execution_end`，维护「当前动作 + 起跑时间戳」
   - 非工具事件直接 return，保持零副作用

2. **`CardKitStream` 增加 `setNote(text)`**
   - 现状：`note` 是构造时 `readonly`，卡片建好后再不能变（`cardkit-stream.ts:65`）
   - 改成可变字段 + 触发一次 PUT；复用既有 `pushIntervalMs` 节流，不新增定时器

3. **耗时刷新用「已有的 tick」**
   - `tick()` 本来就在按 `pushIntervalMs` 跑，在里面判断「当前工具已跑多久」并更新 note 文案即可
   - 不为耗时分针单独开 `setInterval`

4. **文案长度与转义**
   - 参数只截前 60 字符，单行化（换行 → 空格），避免长命令把卡撑爆
   - note 走 `normalizeNote`（`card-builder.ts`），保持既有转义规则

5. **`feishu_ask` 暂停期间不清 note**
   - `pauseForAsk` 时 note 被置为「等你选择」，此时忽略工具事件，避免覆盖用户正在看的提示

6. **轮末清理**
   - `close()` 时清掉当前动作，`steps` 档把清单定格进最终卡

## 5. 测试

只写代码单测（本仓不做需要真机/模拟器的测试）：

| 用例 | 断言 |
|------|------|
| `updateFromEvent` 收到 `tool_execution_start` | note 变为对应档位文案 |
| `progressMode=off` | note 始终为空，零 PUT |
| 工具耗时未超阈值 | 不出现「耗时」字样 |
| 工具耗时超阈值 | 出现「耗时 Ns」且随 tick 递增 |
| `steps` 档多工具 | 清单顺序与 ✅/⏳ 标记正确 |
| `pauseForAsk` 期间来工具事件 | note 保持「等你选择」，不被覆盖 |
| 参数超 60 字符 / 含换行 | 截断且单行化 |
| `parseRuntimeConfigValue("progressMode","xxx")` | 返回 `ok: false` + 可读报错 |

命令：`node --test test/reply-card.test.ts test/cardkit-stream.test.ts`（在 `.pi/ax-feishu-bridge` 下）。

## 6. 分期

| 期 | 内容 | 工作量 |
|----|------|--------|
| P1 | `action` 档 + `progressMode`/`progressTimeoutSeconds` 配置 + 两处入口 | 约 40 分钟 |
| P2 | `steps` 档（执行清单） | 约 30 分钟 |
| P3 | `timeout` 档 + 文案打磨 | 约 20 分钟 |

**P1 即可解决「看起来卡了」的主诉**，P2/P3 是可选增强。

## 7. 未决问题

1. 卡片 note 区在飞书客户端的**渲染行数上限**未实测 —— `steps` 档清单变长时可能被截断，需真机确认后决定是否折叠前 N 条。
2. `progressMode` 默认值给 `action` 还是 `off`？给 `action` 是「默认改善体验」，但也意味着所有人都多一份推送开销。**建议 `action`**，理由是无声沉默本身就是当前的问题。
3. 是否需要**群聊也展示**？当前 `/config` 仅私聊可用，但展示效果本身与群聊无关 —— 建议展示逻辑与配置命令分开，群聊也照配生效。
4. `steps` 档在 `feishu_ask` 之后续段时，清单是重开一份还是延续上一段？建议**重开**（与正文 offset 的分段语义一致）。
