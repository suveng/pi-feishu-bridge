# 飞书进度展示设计（执行过程可见化）

> 状态：**待评审，未开发**
> 范围：`.pi/ax-feishu-bridge`（桥接自身，不是产品需求）
> 目标读者：维护桥接的人

## 1. 问题

### 1.1 现象

Pi 在本机执行长任务时（一次 `bash` 跑 90 秒、连续几十次 `read`），飞书里那张「回复中」卡片
**正文一个字都不动**。用户无法区分「正在干活」和「已经卡死」，只能干等或反复发消息。

### 1.2 根因

桥接**主动丢弃**了工具执行事件。`src/feishu/reply-card.ts:247`：

```ts
updateFromEvent(_event: unknown) {
  // 不展示过程
}
```

而 Pi 侧一直在发这些事件：

| 事件 | 载荷 | 桥接是否消费 |
|------|------|--------------|
| `tool_execution_start` | `toolCallId` `toolName` `args` | ❌ 丢弃 |
| `tool_execution_end` | `toolCallId` `toolName` `isError` | ❌ 丢弃 |
| `text_delta` | `delta` | ✅ 逐字进卡片正文 |
| `message_end` | `message` | ✅ 触发轮末收尾 |

事件其实**已经到了** `updateFromEvent` 里——`PiConversationRuntime.ts:1252` 在 `session.subscribe`
回调中对每个事件都调了一次。所以问题不是「拿不到」，而是「拿到没渲染」。

### 1.3 为什么不能直接塞进 note

`note` 是 `feishu_ask` 用的「等你选择」提示位，**不是**过程展示位：

| 限制 | 位置 | 后果 |
|------|------|------|
| note 超 96 字符截断 | `card-builder.ts:15` `MAX_NOTE_CHARS = 96` | 清单装不下几行 |
| `normalizeNote` 把 `\s+` 压成单空格 | `card-builder.ts:206` | 多行清单被压成一坨 |
| note 与正文**共用同一个 markdown 元件** | `card-builder.ts:61-66` 拼成 `note + "\n\n" + body` | 两者抢同一份长度预算 |

第三条最要命：流式更新只 PUT `elements/content/content`，发的是纯正文（`cardkit-stream.ts:212`）。
把清单塞进 note，就是让清单和正文互相挤占空间。

## 2. 目标与非目标

### 2.1 目标

1. 工具执行期间，卡片上能看到**完整过程清单**（工具名 + 完整命令 + 耗时 + 成败）
2. 一轮结束后清单**整轮保留**
3. 「看多少过程」**可配置**，飞书 `/config` 能改、Pi 侧 `/feishu` 也能改
4. `off` 档完全退回当前行为（零开销、零视觉差异）
5. 清单与正文**互不抢空间**（独立元件）

### 2.2 非目标

- ❌ 不做工具**输出**（stdout / 文件内容）回传
- ❌ 不做思考过程（thinking）展示
- ❌ 不改 Pi 侧扩展
- ❌ 不改 `feishu_ask` 的 note 语义（note 继续只做「等你选择」）

## 3. 设计

### 3.1 核心思路：给卡片加第二个 markdown 元件

飞书官方对「多区域分别流式」的推荐做法：**卡内预先放多个带稳定 `element_id` 的 markdown 元件，
各自调 `PUT /cards/:card_id/elements/:element_id/content`，共享同一条严格递增的 `sequence`。**

我们现状已具备全部前提：

| 需要的能力 | 现状 |
|---|---|
| `schema: "2.0"` | ✅ `card-builder.ts:105` |
| `streaming_mode: true` + `streaming_config` | ✅ `card-builder.ts:96-104` |
| 元件带 `element_id` | ✅ 已有 `element_id: "content"` |
| 全卡共享递增 `sequence` | ✅ `cardkit-stream.ts` 的 `this.sequence` |

所以只需新增一个 `element_id: "progress"`：

```
┌──────────────────────────────┐
│ 🔄 回复中             [停止]  │
│ ── elements/progress ──       │  ← 本设计新增，独立 PUT
│ ✅ read  src/feishu/reply…    │
│ ✅ bash  rg -n tool_exec src  │
│ ⏳ bash  npm test              │
│ ── elements/content ──        │  ← 既有正文，逐字打印不变
│ 我查一下知识库里的…           │
└──────────────────────────────┘
```

**收益**：清单再长也不会挤掉正文；正文继续按 `print_step` 打字机输出。

### 3.2 数据流

```
Pi session 事件
   tool_execution_start / tool_execution_end
        ↓  session.subscribe → run.status.updateFromEvent(event)
   ReplyCardStatus（状态机）
        ↓  累积「过程清单」文本，节流后调用
   CardKitStream.setProgress(lines)
        ↓  PUT .../elements/progress/content（全量文本）
   飞书卡片 progress 元件刷新
```

正文路径完全不动：`text_delta` → `append()` → `PUT elements/content/content`。

### 3.3 配置项

新增三个白名单配置（进 `RUNTIME_CONFIG_KEYS`，即天然获得 `/config` + `/feishu` 两个入口）：

| key | 取值 | 默认 | 含义 |
|-----|------|------|------|
| `progressMode` | `off` \| `steps` \| `action` \| `timeout` | `steps` | 过程展示档位 |
| `progressMaxLines` | 整数，1–100 | `50` | 清单最多保留多少行，超出折叠成一行计数 |
| `progressTimeoutSeconds` | 正整数 | `30` | 超过该秒数才显示耗时（`timeout` 档与 `action` 档共用） |

**各档行为**：

| 档位 | progress 元件显示什么 | 推送时机 |
|------|----------------------|----------|
| `off` | 元件不出现（等价于现状） | — |
| `steps` | **累积清单**，每行一个工具，带 ✅/⏳ + 完整命令 + 耗时；超 `progressMaxLines` 折叠 | 工具开始/结束时更新 |
| `action` | 只显示**当前一个**工具那一行（旧的被覆盖） | 工具切换时更新 |
| `timeout` | 平时不显示，单工具超阈值才出现 `⚠️ bash 已执行 45s…` | 超阈值后每 5s |

> 默认给 `steps`：这次改造的诉求就是「想看全部过程」。
> 若嫌推送开销大，`/config progressMode action` 一行即可降级。

**清单行格式**（每行一条，单行化，不折行）：

```
✅ bash   rg -n "tool_execution" src/            · 1.2s
❌ bash   npm run build                          · 8.4s  (退出码 1)
⏳ edit   src/feishu/reply-card.ts
```

- 图标：`⏳` 进行中 / `✅` 成功 / `❌` 失败
- 工具名左对齐补齐（便于扫读）
- 命令：**完整命令**，但须**单行化**（换行 → `␣`）并设单行上限
  `progressCommandChars`（常量，默认 200 字符，超出中部省略）
- 耗时：工具结束时写入；进行中的不显示耗时（避免每行都在跳动）

### 3.4 配置入口（两处，同一份 overrides 文件）

两条路径都指向 `~/.pi/agent/feishu/runtime-overrides.json`：

**飞书侧（已有命令，零改动）**

```
/config progressMode steps
/config progressMaxLines 80
/config progressTimeoutSeconds 60
/config clear progressMode
```

**Pi 侧（`/feishu` 命令扩展）**

```
/feishu progress steps        # 等价于上面第一条
/feishu progress off
/feishu progress              # 打印当前档位 / 行数上限 / 阈值
```

`/feishu` 子命令走 `src/adapters/pi/index.ts` 的既有 command 分发，扩一处 switch 分支。

### 3.5 实现点

1. **`buildCardKitCardJson` 增加 progress 元件**
   - `progressMode !== "off"` 且清单非空时，在 `content` **之前**插入
     `{ tag: "markdown", content: 清单, element_id: "progress" }`
   - `off` 档不插入 —— 元件不存在，零开销

2. **`CardKitStream` 增加 `progress` 能力**
   - 私有字段 `progressText` + `lastProgressSent`
   - `setProgress(text)` 只改字段；由既有 `tick()` 统一推送（**不为 progress 单独开定时器**）
   - `tick()` 改为：正文有变化 PUT `content`，清单有变化 PUT `progress`，两者共用 `this.sequence`（**必须共享**，官方要求全卡严格递增）
   - 注意：`tick()` 现在的早退条件是 `fullText === lastSent`，加了 progress 后要改成二者都相等才早退

3. **清单文本由 `ReplyCardStatus` 维护**
   - `updateFromEvent` 里维护 `Map<toolCallId, {toolName, args, startedAt, ok?}>` 插入顺序列表
   - 渲染成上表格式的单行文本
   - 超 `progressMaxLines` 时：保留首行 + 最后 N-2 行 + 中间一行 `…（中间 28 步已折叠）`

4. **`tick()` 里的耗时刷新**
   - `steps` 档只给**已结束**的行写耗时；进行中的行不带耗时，避免每 push 都变（变一次就是一次全量上屏）
   - 需要显示「已跑多久」时（`timeout` / `action` 档）沿用既有 tick 节奏

5. **`progressMode: off` 的兜底**
   - 不构建元件、不调用 `setProgress`，路径与当前代码完全一致

6. **轮末收尾**
   - `close()` 时清单**定格**进终态卡（`buildCardKitCardJson` 终态分支也要带 progress 元件）
   - 进度元件在终态卡里保持只读展示，不再更新

7. **`feishu_ask` 不影响清单**
   - `pauseForAsk` 只改 note 与 status，清单继续保留在 progress 元件里（用户答完续段时能看到之前干了什么）
   - 未决问题第 4 条讨论续段是延续还是重开

### 3.6 官方硬约束（实现时必须遵守）

| 约束 | 值 | 对我们的影响 |
|------|-----|--------------|
| 卡片 JSON 总量 | **≤ 30KB**（错误码 `200860`） | **清单必须限量**，这是 `progressMaxLines` 存在的真正原因；正文也吃这份预算 |
| `sequence` | 全卡所有操作**共享**、严格递增 | 两个元件的 PUT 必须共用一个计数器 |
| 流式更新文本 | `content` 是**全量文本**，非增量 | 每次发完整清单 |
| 打字机触发条件 | 旧文本是新文本的**前缀**才续写；否则全量直接上屏 | 清单状态翻转（⏳→✅）会直接上屏、不重复打字，**符合预期** |
| 卡片元件总数 | ≤ 200 | 无影响 |
| 交互期间 | 用户点击卡片回调期间**无法更新卡片** | 用户点「停止」瞬间进度可能停一拍，可接受 |
| 客户端版本 | ≥ 7.20 | 低于则显示兜底提示 |

## 5. 测试

只写代码单测（本仓不做需要真机/模拟器的测试）：

| 用例 | 断言 |
|------|------|
| `buildCardKitCardJson` + `progressMode=steps` | elements 里含 `element_id: "progress"`，且在 `content` 之前 |
| `progressMode=off` | elements 里**不含** progress 元件 |
| `updateFromEvent` 收 `tool_execution_start` | 清单新增一行 ⏳，命令为完整命令 |
| `tool_execution_end`（成功/失败） | 该行变 ✅ / ❌，并写入耗时 |
| 同一 `toolCallId` 重复事件 | 不重复插行（按 id 去重） |
| 命令含换行 / 超 200 字符 | 单行化 + 中部省略 |
| 超过 `progressMaxLines` | 出现折叠行，且行数回落 |
| `tick()` 双路 | 正文与清单各自变化都能触发 PUT，且 `sequence` 连续递增 |
| 清单无变化 | 不额外 PUT（节流生效） |
| 终态卡 | progress 元件仍在，内容为定格清单 |
| `parseRuntimeConfigValue("progressMode","xxx")` | `ok: false` + 可读报错 |

命令：`node --test test/reply-card.test.ts test/cardkit-stream.test.ts test/progress-note.test.ts`
（在 `.pi/ax-feishu-bridge` 下）。

## 7. 未决问题

1. **30KB 体积预算未实测**：正文 + 50 行清单会不会触顶？需要 P3 真机压测（造一次 100 工具调用的轮次）。
   若触顶，降 `progressMaxLines` 默认值或对清单做更激进的截断。
2. **默认档位定 `steps` 是否太吵**：默认 `steps` 是「改善体验」，代价是每次都建第二个元件。
   备选默认为 `off`、让用户显式开。**建议 `steps`**：沉默本身就是当前的问题。
3. **群聊是否展示**：`/config` 仅私聊可用，但展示逻辑与配置命令应分开 —— 群里也照配生效（展示正常，改配置需私聊）。
4. **`feishu_ask` 续段清单语义**：续段（`回复（接上条）` 新卡）时，progress 清单是**重开一份**还是**延续上一段**？
   建议**重开**，与正文 offset 的分段语义一致。
5. **慢工具期间清单无变化导致「还是看起来卡了」**：`steps` 档下若某个工具跑 5 分钟，清单也只多一行 ⏳ 不带耗时 —— 是否要给进行中的行加实时耗时？
   加的话会带来持续 PUT，需要权衡。
